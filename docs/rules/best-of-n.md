# 并行尝试取优

一次尝试是一个样本，不是答案。三到五次尝试通常比修复一个跑偏的初版更便宜。

## 何时启用

非平凡的可运行产物一次尝试可能落错形状；用户要「试几个版本」「三选一」。

只用于能跑起来的东西。接口设计、界面方向这类不可运行的提案，按流程的多方案对比法产出与比较，不套用本规则的实跑打分。

## 做法

1. 定任务。写一份所有尝试原样收到的提示。私下写 3 到 6 条具体、可核对的标准，尝试看不到这份标准。
2. 定 N。默认 3，设计空间宽用 5。每个尝试给独立输出位置，如一个工作树或独立临时目录。
3. 一次并行开 N 个子代理，给提示、共享上下文与输出路径。要每个交产物加一段被拒方案的简短说明。没有子代理就逐个在全新上下文里跑。
4. 逐个检查。跑它的构建、测试或快速探针。带输出记录过或不过。跑不起来的淘汰。
5. 按标准给幸存者打分。选整体结构最好的当底稿。结构胜过打磨。
6. 列出其它尝试的具体强项：一个测试、一个边界情况、一个更干净的函数。只嫁接这些进底稿。不整文件合并。
7. 在嫁接结果上重跑完整检查并贴输出。

## 停止

- 嫁接后的结果通过所有检查，并报告底稿、嫁接内容与分数。
- 澄清提示后重跑一次仍没有尝试通过。报告什么失败了。

## 红线

- 绝不看尝试自己的总结来选。跑它来选。
- 打分前不让一个尝试看到另一个。
- 最终检查通过前保留落选尝试。
