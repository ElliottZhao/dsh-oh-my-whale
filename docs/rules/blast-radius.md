# 改动的影响半径

列出调用方很容易。难的是找到文本搜索看不见的破坏，然后用一次实跑而不是一通论证证明改动安全。

## 何时启用

要发一个高风险或来路不明的改动；用户问「这会破坏什么」；改动碰到共享数据、公共接口、时序或配置。

PR 正文里的影响半径字段用一句话写影响范围；本规则是高风险改动的取证方法，不是那个字段的填写模板。

## 做法

1. 读改动：diff 本身、它新增修改或删除的符号、以及 diff 没写出来但行为已经变了的部分。
2. 找出这条改动之所以安全的一两个关键事实。比如「这只删已经过期的缓存项」。多数风险在这条成立时消掉。把力气花在这里。
3. 去搜索停下的地方看：
   - 读你调用的库在锁定版本下的源码。
   - 看时序：异步顺序、销毁、重试。
   - 追离开代码的数据：API 响应、数据库列、文件格式、配置、别的语言读同一份数据的地方。
4. 给每条关键事实定证据级别：
   1. 你说是这样；
   2. 指到了真实文件与行；
   3. 追出失败路径并证明到不了；
   4. 写了一个跑真实代码、错了会大声失败的脚本或测试；
   5. 在运行的应用里复现了。
5. 便宜时把关键事实推到第 4 级。通常就是一个小脚本调用那个确切的函数。
6. 报告：关键事实、证据级别与命令输出、找到的真实破坏、以及哪些没有证明。

## 停止

- 每条关键事实都到第 4 级，或说明了为什么到不了，报告写成。
- 或找到真实破坏。带复现报告并停止。

## 红线

- 有说服力的文字不是证明。给输出。
- 这里不修东西。修复交回正常流程。
