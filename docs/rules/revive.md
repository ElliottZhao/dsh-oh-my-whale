# 复活旧 PR

更新的是想法，不只是分支。干净的 rebase 不证明这个 PR 仍然该存在。

## 何时启用

用户要求 rebase、刷新、更新或复活一个陈旧的 PR。

## 做法

1. 拉最新基线、PR head 与相关分支。
2. 记录 PR URL、状态、基线、头分支、头提交哈希、作者、检查与评审状态。读标题、正文、关联 issue、提交、线程与完整 diff。
3. 一句话写下 PR 的目标。
4. 找 merge base，读基线那之后落地的内容。按同一问题搜已合并与打开的 PR。
5. 每条都用证据（提交、PR 或文件路径）回答：
   - 这个问题是不是已经被解决了？
   - 它依赖的 API、类型、schema 或结构变了吗？
   - 它改的代码被移走、删掉或简化了吗？
   - 落地会不会带回旧行为，或让一件事有两种做法？
   - 收益还值这份维护吗？
6. 给一个结论：
   - **复活**：目标与形状都还成立。走第 7 步。
   - **重做**：目标成立，形状不成立。说清最小的重写并停下，除非用户同时要求做重写。
   - **关闭**：被取代或不再值得。给证据并停下。不自己关。
7. 复活时，在记录的头提交上开干净工作树，变基到新基线。按 PR 的目标与基线的新规则解决冲突。
8. 对旧新两套提交跑 `git range-diff`。确认没丢意图中的改动，也没把已落地的带回来。
9. 跑碰到范围的聚焦检查。每个失败标为真实、既有或基础设施。
10. 用 `--force-with-lease=<branch>:<old 头提交哈希>` 推送。
11. 先报结论，再报基线变化、冲突、推送结果、检查、剩余决策与 PR 链接。

## 停止

- 给出三个结论之一并写完报告。
- 冲突暴露产品或设计分歧。停下重新考虑结论。
- 租约失败。重新拉取，重做第 4 到 6 步一次。再失败就报告。

## 红线

- 脏工作树是用户的。不 stash 不丢弃。
- 不合并、不关闭、不改基线分支。没有租约不强制推送。
- Git 没冲突不等于 PR 是最新的。
- 分开说你核实过的事实与你的判断。
- 只在被要求时发 PR 评论，并走 `pr-comments.md`。
