# 盯 PR

让一个 PR 走到绿且评审完，少制造噪音。

## 何时启用

用户要求盯、监控或照看一个 PR。

## 做法

1. 先处理已有的事：失败的检查、上次推送之后的评论。
2. 起一个看护进程，放在后台任务或监视工具里，让每行输出唤醒你。没有这种工具就作为一条长时间前台命令跑。不自己写 sleep 轮询，一个 PR 只用一个看护。
3. 每个事件都先读源头再改代码。判断这条发现是否真实。
4. 真缺陷或持续集成失败：做最小修复，本地跑失败的那项检查，推送，重启看护。
5. 误报或超范围请求：通过 `pr-comments.md` 回一句简短理由，解决线程，列为后续。
6. 把真实的测试失败与基础设施抖动分开。抖动先重跑一次再下结论。
7. 基线移动或分支落后就变基，用 `--force-with-lease` 推送，重启看护。
8. 宣布 PR 就绪前 `git fetch` 再读一遍。不能是 BEHIND 或 DIRTY。

## 停止

- 看护给出就绪（检查绿、分支可合、没有改动要求）或已合并。
- 六轮修复加推送仍不绿，报告还差什么。
- 另一个 PR 让这个过时。停下，关之前先问。
- `gh` 报限流：查 `gh api rate_limit`，等重置换一次。不循环。

## 红线

- 每个 PR 一个看护。绝不自己写 sleep 轮询循环。
- 事件不需要动作就不说话。不发「仍在等待」。
- 只有用户要求才合并。否则报告就绪。
- 单票据 PR 保持小，优先删减或收窄代码的修复。多票据集成流程的 PR 以规格为范围单位，不受这条限制。
