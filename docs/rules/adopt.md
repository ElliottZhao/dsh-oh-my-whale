# 接手别人的工作

把别人的活当成自己的做完，但把功劳留给他们。

## 何时启用

用户说「接手」「接着做」「把这个 PR 做完」，或一条旧的工作线程交到你手里。

## 做法

1. 完整读来源：PR、分支或线程的描述、提交、评审评论，以及用户后来的更正。
2. 找真实当前状态：头提交哈希、未提交改动、未关闭的评审发现。把交接说明当线索而非事实。
3. 一句话写下原始目标。
4. 选在哪干活。默认在原始提交上开一个新分支，你的修复作为独立提交。只有用户要求才原地继续或叠加。
5. 先跑 `revive.md`，把工作对齐到基线。
6. 修到满足原始目标。能简化就简化，保留每个意图中的行为。
7. 自己验证。复现原问题，再证明修好了。跑真实流程，不只 mock 测试。记录命令与输出。
8. 再读一次来源 PR，你干活期间它可能变了。
9. 要 PR 就按 `pr.md` 开，再按 `watch-pr.md` 盯。任何回复走 `pr-comments.md`。
10. 报告：继承了什么、改了什么、怎么验证的、如何保留署名、还什么没做。

## 停止

- 目标达成、验证过、报告完。
- 目标不清楚，或做完需要产品决策。问用户。
- 验证连续三次因同一个问题失败。报阻塞。

## 红线

- 保留原始 Git 作者与共同作者 trailer。在描述里点名贡献者并链接原 PR。
- PR 会被 squash 时，在 squash 信息里保留人类共同作者行。只用可核实的身份，绝不猜邮箱。
- 不要因为旧代码存在就替它辩护。不加无关功能。
- 未经许可不编辑、合并或关闭原 PR。
- 明说哪些没验证。
